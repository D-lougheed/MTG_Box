# Implementation plan — Slices 2-5

**Spec:** `docs/superpowers/specs/2026-09-05-slices-2-5-design.md`
**Started:** 2026-09-05

## Approach

The four remaining slices touch mostly-disjoint code, so they were built in
parallel by separate agents rather than in roadmap order. The dependency that
would have forced serialisation — every slice needing the card data layer —
was removed by writing `src/mtgkiosk/cards.py` (the `Card` record and all
queries) up front as a fixed contract, before any parallel work started.

Shared files are **not** touched by feature work. `web/index.html`,
`web/css/style.css` and `src/mtgkiosk/app.py` are integrated centrally,
because three separate frontend features all need a view container, a
`<script>` tag and an API route, and having several agents edit those
concurrently would be the one guaranteed source of conflicts.

Frontend features therefore build their entire UI in JavaScript into a single
root element, and expose an `on<Feature>Shown()` hook. `showView()` looks that
hook up by name at call time and calls it inside a try/catch, so a feature
script that fails to load or throws on show cannot take the rest of the menu
down with it — on a kiosk, a broken sub-screen must not cost you the life
counter mid-game.

## Corrections made during the build

Recorded here for the same reason Slice 1's plan recorded its own: the
mistakes are the part worth keeping.

**`search()` selected a computed `rank` column.** `_row_to_card` feeds every
selected column straight into `Card(...)`, so the extra column raised
`TypeError: unexpected keyword argument 'rank'` on any search. Moved the CASE
expression into `ORDER BY`, where it never becomes a result column. Caught by
the first route-level test written against a real database — the module's own
unit tests had not covered a populated search.

**`creatures_by_subtype()` truncated alphabetically.** It ordered by name
before applying `LIMIT`, so any subtype with more creatures than the 500-card
pool limit — Human, Wizard, Soldier, Spirit — yielded only the
alphabetically-first slice, and every generated horde would have been full of
cards beginning with "A". Now orders by id (a UUID), which is an arbitrary but
stable ordering, so truncation samples the pool instead of biasing it. Found
by the horde agent while reading the query it depended on, not by a test.

**The horde spec contradicted itself.** `build_deck` was specified with both a
`size` parameter and a difficulty table that also sets size. The difficulty
table won; `size` was dropped from the signature.

**`available_subtypes` raises rather than returning `[]`** when the database is
missing, diverging from `cards.subtypes_with_counts`. That lets
`GET /api/horde/subtypes` distinguish "no database yet, offer a download" from
"database is fine but nothing clears the threshold" — two states that need
different UI.

## Found by review, after the first push

Two review passes ran against the integrated build, one on the backend and one
on the frontend, both with access to the real database and the running app.

**Planeswalker loyalty never printed.** `card_label._stats()` paired
power/toughness/loyalty by face index, on the documented assumption that empty
face positions are preserved. `ingest._face_value` drops them — and says so in
its own docstring. Both docstrings were individually reasonable and mutually
incompatible, so all 13 creature-front/planeswalker-back cards printed "0/2"
instead of "0/2 // 5". The module's own test asserted the right answer using a
hand-built `Card` in a wire format the ingest cannot emit. Fixed, plus
round-trip tests that take a Scryfall entry through the real ingest and out
through `_stats`, so the two modules' assumptions are asserted against each
other rather than each against itself.

**A schema-mismatched database reported healthy, then 500'd.** `count()` ran
`COUNT(*)`, which succeeds against a table with any columns, so `is_available()`
said yes and every real query then raised. The status endpoint said fine, the
horde tribe list populated, and the feature failed at the moment of use with no
signal telling the UI to offer a rebuild. Any future column added to `SCHEMA`
would have put every deployed Pi in that state. `count()` now probes the real
column list.

**LIKE-wildcard injection into the subtype query.** `creatures_by_subtype`
interpolated the caller's string into three LIKE patterns unescaped, and that
string arrives from a request body: `{"subtype": "%"}` returned a 60-card deck
spanning every tribe in Magic, labelled as subtype `%`.

**"Saga" was offered as a creature tribe.** Subtypes were harvested from any
card whose *whole* type line mentioned Creature, so a transforming Saga
contributed "Saga". There are 50, over the threshold, and the resulting deck was
more than half non-creatures on the visible face.

**An orphaned horde repeat timer drained the next game.** The press-and-hold
timer was cancelled only by window `pointerup`, and `adjustHordeLife` re-read
the current game each tick. Holding −1, abandoning, and starting a new game took
the *new* game's player from 20 to −2 in 1.5s.

**A stale lookup response reopened the keyboard over another view.** The
staleness token was bumped on entering card lookup but never on leaving, so a
slow `/api/cards/status` could call `showKeyboardFor` after the user had already
moved on — burying 6 of the life counter's 13 controls with no way out. The
shell now runs a teardown hook on the view being left.

**Repeat timers weren't keyed by pointer id**, so two players adjusting life at
once froze each other — the normal case at a 4-8 player table.

**The Windows rename bug the review predicted, then hit.** `os.replace` cannot
replace a file another process holds open, and the design guarantees a reader:
the UI polls status throughout the ingest. It cost a real multi-minute download
mid-session and surfaced as a generic failure that read like a network problem.
Now retried with backoff.

## Deferred, with reasons

**Pool limit of 500 creatures per subtype.** Loading every Human into memory on
the Pi to sample the true full pool is not worth it; 500 distinct creatures
already far exceeds what an 80-card deck can show.

**No JS test runner.** Frontend behaviour is verified by driving the real UI in
a browser at 800x480. Adding a runner would mean adding a build step, which
this project has deliberately avoided since Slice 1 — the update mechanism is
`git pull` plus a restart, and `npm install` on a Pi over wifi is the fragile
step that breaks at the worst moment.
